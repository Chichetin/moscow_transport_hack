## Как считает судья

- Эталон — `/localization/kinematic_state` (`nav_msgs/Odometry`, 50 Гц). В наших bag этого
  топика нет.
- Пары — `message_filters.ApproximateTimeSynchronizer`, допуск 0,05 с, очередь 100, QoS
  sensor_data. `frame_id` не проверяется. Скорость — `velocity` против
  `twist.twist.linear.x`, позиция — x, y, z и 3D-норма; RMSE и max, отчёт каждые 5 с.
- **Пакет сообщений судьи — только `VelocitySensor`.** Если наш `src/` собрать в этом
  workspace, `ros2 bag play` пропускает `/vehicle/driver_position_cmd` (WARN о typesupport),
  и до фикса нода падала на импорте `DriverControllerCommand` → `n=0`, 0 баллов (#184, D-093).

## Как гоняли исторические версии

Чистый `ros:humble-ros-base`, `--network=none`, реальный темп. Workspace = наш `src/*` +
`check-code/src/checker_ros`; для варианта «пакет судьи» ещё и `check-code/src/tram_vehicle_msgs`
поверх. В одном контейнере: `ros2 launch tram_odometry odometry.launch.py`,
`ros2 bag play bags/30618_88aea4d9` и `ros2 run hackathon_solution_checker metrics`.
Итог — последняя строка отчёта судьи. Сохранившееся описание не содержит полного
исполняемого сценария и логов всех команд; при финальном прогоне evaluator должен
записать их вместе с точным SHA и путями артефактов.

  Пример организаторов также использовался для исправлений и калибровки;
  слово «независимый» в исторических отчётах не означает независимость
  итоговой системы от этого примера.
- кандидат `cfe09a5` — невлитый кандидат: 4,2 м/с, окно 15–35 м против
  4,95 м/с и 15–55 м в `194a8f7`. Его расчётные улучшения не являются

  3,754 м/с и первое превышение 4,2 на 46,008 м дают номинально около 11 м
  запаса; это данные аудита кандидата `cfe09a5`, не гарантия неизвестного разгона.
- R-06 (#191): переданный аудит train `30639_d3c43d69` обнаружил along/cross

## Аудит порядка запуска: короткие ROS-пробы

В переданном startup-аудите runtime SHA не зафиксирован. Его RMSE не включаем
в таблицу точности выпущенной версии. Зафиксирован сценарий отказа: первые
5 с GNSS по header из буферизованной пачки закончились к 0,9195 с playback;
нода, запущенная после 3 с, пропустила все разрешённые fix. Эти времена —
неатрибутированный startup-аудит, не измерение `8626dde`. После закрытия окна
локальный `odom` нельзя сравнивать с абсолютным эталоном. Расширять окно GNSS
для такого запуска нельзя; потерянные сообщения оно всё равно не возвращает.

Нужны готовые нода, судья и записывающие подписчики **до playback**.
До первого входа ждать выходов бессмысленно: проверяют подписки через
`ros2 topic info -v /sensing/gnss/master/fix` и
`ros2 topic info -v /vehicle/front_bogie_velocity`.
Каждый повтор bag начинается со свежей нодой. Во всех терминалах подключают
сборку выбранного workspace; `source` сам по себе не обновляет устаревший `install/`.
Порядок — [README](../../README.md#2-запуск).

## Что нужно для финального кандидата

Завершённые измерения базы: holdout `8626dde`, оба полных запуска `3b1f1d9`,
длинный стенд `8626dde` ([точные значения и provenance](2026-09-27-pr196-docs.md)).
Для документационного PR эти прогоны повторно не запускались.

При изменении runtime требуется закрепить новый SHA, записать сборку из чистого
архива, параметры/карты и команды; повторить соответствующие holdout/stress,
оба варианта сообщений у судьи и стенд 2 CPU / 512 МБ без сети. Записать по
каждому выходу пары, задержки, частоты и ресурсы, первый frame позиции,
порядок запуска и исключения. Отдельная проверка позднего старта должна
указывать доступность разрешённых fix; она не заменяет штатный запуск.

На сдаваемом commit нужны зелёные раскладки (включая `judge_msgs_*`), CI и
формальный гейт. A2/E6 уже закрыты PR #199 по отдельному протоколу #96.
Подготовка питча не означает прохождения гейта на этом commit, создания тега
или отправки формы.
