# Runner сценариев судьи: порядок запуска, последовательные bag, поздний старт (#201, #200)

27.09.2026, IR630. Проверяется **наш** порядок запуска в контейнере жюри, а не порядок на реальном
стенде жюри. Успешный runner подтверждает работу при порядке «свежая нода → входные подписки
готовы → единственный `bag play`». Чтобы закрыть #201, нужно отдельно подтвердить, что стенд
жюри обеспечивает этот порядок: `check-code/scripts/run.sh` держит контейнер через
`sleep infinity` и порядок ноды и player не задаёт (M1hairu, `docs/handoffs/2026-09-27-ir630.md`).

## Команда

```bash
bash tools/submission/judge_runner.sh            # A=30618_0e41eac3, B=30618_68847170 (оба train)
```

Код берётся из `git archive HEAD`. Образ `tram-odom:jury`: `--cpus=2 --memory=512m --network=none`,
не root, один контейнер на все сценарии. Отчёт с логами, `exit.tsv`, `times.tsv`, записью
`/result/*` и `report.json` лежит в `out/submission/judge-runner-<commit>-<YYYYmmddTHHMMSS>/`. Код выхода 0 означает,
что каждый сценарий совпал с ожиданием.

Протокол одного сценария (`judge_runner_inside.sh`):

1. Проверка, что ни одного процесса `odometry_node` от прошлого сценария не осталось (иначе ошибка).
2. `ros2 bag record /result/*`, затем `ros2 launch` свежей ноды (свой process group).
3. `wait_ready.py`: у всех шести входных топиков есть подписчик в графе, у `/result/*` —
   запись. Таймаут 20 с, при нём `ready_exit=1`.
4. Единственный `ros2 bag play`, 2 с на дочитку, SIGINT записи и ноде (только своим группам).
   Не завершились за 15 с — SIGKILL и строка в `errors.txt`.
5. `check_recording.py`: типы `/result/*` и stamp выхода = stamp входа.

Exit codes не подменяются: отчёт показывает отдельно код `ros2 launch` и код дочерней
`odometry_node` из `node.log`. Нода, умершая до остановки, ненулевой exit play/ready/check,
живой чужой процесс ноды, частота ниже 10 Гц, неполное покрытие входного bag выходами
или frame не по ожиданию дают `fail`. Ненулевой код дочерней ноды после SIGINT runner
показывается как warning. Эти условия покрыты тестами `tools/submission/tests/test_judge_runner_report.py`.

Сценарные bag — первые 90 с записи train bag (`make_scenario_bags.py`). Выбор сценария
зависит от `header.stamp`, а не от времени записи:

| bag | из | что изменено |

| `a_crop`, `b_crop` | A, B | только обрезка |

## Что это закрывает и что нет

- **Порядок «свежая нода на каждый bag»** работает: два разных bag подряд в одном контейнере дают
  `map` с ошибкой меньше 2 м, bag без GNSS после bag с GNSS идёт в `odom` без старого якоря,
  GNSS раньше первой тележки тоже выставляет `map`.
- **Поздний старт при коротком начальном GNSS теряет привязку**: ожидаемый отрицательный
  результат, вся позиция в `odom`. Выбор конечной по скалярному пути колёс его не
  восстанавливает, и в код его не вносим (решение пользователя, 27.09).
- **#201 остаётся открытым**: нужно подтверждение, что стенд жюри запускает ноду и дожидается
  подписок до `bag play`. #200 тоже остаётся открытым: одна нода на несколько bag здесь не
  проверяется, runner всегда поднимает свежую ноду. Явный reset появится в runner только после
  согласования API с Ivana-banana.
- Поддержка overlap, `--loop`, seek и нескольких одновременных player не заявляется.
