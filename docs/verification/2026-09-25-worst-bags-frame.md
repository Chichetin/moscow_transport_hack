## Что нашли

`tools/eval` строит эталон только по fix статуса 2, если они есть в bag, а начало ENU — первый такой
fix со stamp ≤ конца окна, иначе первый такой fix вообще (D-020). `PathTracker` ставит начало frame
`map` в первый fix статуса 2 окна, иначе в первый валидный (контракт §2, D-030). Если в окне только
статус 0, а статус 2 появляется позже, начала расходятся на путь между этими точками.

## Выводы

- Два «худших bag» holdout — **артефакт системы координат эталона**: сдвиг начала 2012 и 1239 м
  совпадает с их pos3d RMSE в eval (2011 и 1237 м). В своей системе координат модель на них ошибается
  медианно на 1,9 и 1,4 м. Среднее along RMSE по holdout 73 м — из-за этих двух bag.
- У `30618_0686195f` и `30618_defd0170` статуса 2 нет вообще: эталон строится из статуса 0 с его
  шумом и сдвигами 1–9 м (D-020) — отсюда pos3d 10–13 м при горизонтальной ошибке 4–9 м.
- У `30639_4285f2bc` в своей системе координат p95 32 м и max 74 м, 4,5 % точек дальше 50 м от fix
  статуса 0 — остаётся разобрать по графикам (E3, #16); это не выставка на встречную колею.
- Исправление eval — #70 (начало эталона = первый валидный fix окна). Что делает судья — вопрос 4
  в #23: если судья берёт начало так же, как eval сейчас, на таких bag ошибка неустранима без
  GNSS после окна.

## Скрипты

```python
# diag_origin.py <bag>... : статусы в окне и смещение первого статуса 2
msgs = B.read_bag(B.data_dir() / name); win = B.gnss_window_end(msgs, B.default_gnss_window())
fx = [(stamp, status, lat, lon, alt) for master fix]
first_any = first fix with t <= win and status >= 0;  first2 = first fix with status == 2
offset = hypot(geodetic_to_enu(first2, origin=first_any)[:2])

# diag_ownframe.py <bag>... : ошибка в frame трекера
odo = B.default_odometry(); feed msgs, skipping GNSS after win; collect (t, x, y)
F = master fixes with status >= 0 -> geodetic_to_enu(origin=first_any)
nearest estimate within 0.05 s -> hypot(dx, dy): median, p95, max, share > 50 m
```
