### Выделено: сценарии хуже базы больше чем на 10 %

**`noise` — регресс, требует внимания.** Медианная добавка к пику ошибки скорости выросла
на 59 % (0.453 → 0.720 м/с), пик скорости — на 17.5 % (max 2.653 → 3.118 м/с). Хуже того,
**впервые появляются 2 из 26 bag, где позиция не восстанавливается до конца записи**
(`pos_recovery_s = null`), на базе таких bag не было ни одного:

| bag | pos3d excess (было→стало) | pos recovery (было→стало) |
|---|---|---|
| `30618_082f1d65` | 1.129 → 2.548 (+126 %) | 0.027 с → **не восстановилось** |
| `30639_0ab96c59` | 0.990 → 2.306 (+133 %) | 0.039 с → **не восстановилось** |
| `30618_a869780d` | 2.723 → 4.715 (+73 %) | 10.35 с → 10.35 с (восстанавливается, но пик выше) |
| `30618_27e994fc` | 0.840 → 1.421 (+69 %) | 0.033 с → 0.033 с |
| `30618_67b89902` | 0.310 → 0.394 (+27 %) | восстанавливается на обоих |

(Данные — `stress.json` каждого прогона, поле `bags.<bag>.noise`.)

Оба bag с не-восстановлением короткие/аномальные и в holdout-таблице уже худшие по
`cross_rmse`/малой дистанции (`30618_082f1d65` — 0.445 м дистанции, `30639_0ab96c59` —
1.99 м), т.е. это очень короткие фрагменты, где 10 с `noise`-события — почти весь bag;
тем не менее рост пика и появление не-восстановления — реальный регресс устойчивости к
шуму тележек, а не только артефакт коротких bag: `30618_a869780d` и `30618_27e994fc` —
полноразмерные bag (>5 км), где пик тоже вырос на 69–73 %.

**`gap_70` — пограничный регресс по position excess.** Медианная добавка к пику позиции
выросла на 41 % (0.237 → 0.333 м), но восстановление везде происходит (`0 → 0`
не-восстановлений), и абсолютные величины небольшие (десятые доли метра — единицы метров).
По bag: `30639_50956d6e` 0.010 → 0.255 м (+2399 %, на фоне почти нулевой базы), `30639_9f0b519f`
0.062 → 0.343 м (+451 %), `30618_a53d5f6f` 0.237 → 0.645 м (+172 %) — на 70-секундном
пропуске тележки положение расходится сильнее, но не срывается.

**`spike` — один bag с большим относительным приростом на фоне почти нулевой базы**:
`30639_50956d6e` pos3d excess 0.010 → 0.171 м (абсолютно небольшой прирост, база была
近-нулевой). Медиана по сценарию в целом лучше базы (0.082 → 0.038 speed excess), общий
вердикт по `spike` — не хуже.

**`outlier`** — без регрессов, все показатели лучше базы.

## Вывод для merge

По holdout (D-012) — **не хуже, а строго лучше** по всем главным метрикам
(speed_rmse −44 %, speed_mae −39 %, drift_pct −31 %, along_rmse −8 %); падений нет.

По stress — **есть реальный регресс устойчивости к шуму тележек** (`noise`): медианный
пик ошибки скорости и позиции вырос на 41–59 %, и впервые 2 из 26 bag не восстанавливают
позицию до конца записи (на базе — 0). `gap_70` тоже хуже по добавке к пику позиции
(+41 % медиана), но без срыва восстановления. Это не блокирует merge по формальному
критерию D-012 (он про holdout, не про stress), но фильтр даёт более резкий/долгий выброс
при синусоидальном шуме обеих тележек и при длинном (70 с) пропуске — стоит завести
отдельную issue на разбор чувствительности фильтра к `noise`/`gap_70` до финальной сдачи,
если это не было учтено в PR намеренно (trade-off ради выигрыша в штатном ходе).
