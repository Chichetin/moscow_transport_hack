# Как работают участники и агенты

Пять равноправных участников, у каждого свой Claude Code. Координатора и
оркестратора нет: общий список задач — GitHub Issues, общая точка стыковки — контракты
(`docs/contracts.md`), общий судья — `tools/eval` на holdout (D-012, D-013).

## Одна сессия — одна issue — один worktree

```bash
gh issue list --search 'no:assignee label:area:core-slip'   # свободные задачи области
gh issue edit 12 --add-assignee @me                         # взял — видно всем сразу
claude -w 12-slip-detector                                  # сессия в .claude/worktrees/12-slip-detector
```

Обычно это делает сам агент: промпт 2 из `docs/onboarding.md` выбирает свободную issue
по тем же правилам, назначает её, создаёт worktree через `git worktree add` и входит в
него (EnterWorktree с `path`), а человека зовёт только в случаях из списка «Стоп».

Перед тем как взять: `session-context.sh` в начале сессии печатает мои issues и занятые
области. Если `area:` уже у кого-то в работе, эту issue не берём, берём другую. Когда все
зависимости из «Зависит от #…» ещё не в `main`, работа идёт на заглушке, и в PR это
помечено.

Основная сессия участника ведёт свою issue: разбирает её с человеком, решает, что
делегировать, собирает отчёты субагентов и отвечает за PR. Модель по умолчанию `sonnet`
(`.claude/settings.json`). На математику модели и фильтра (вывод уравнений, якобианы EKF,
наблюдаемость, разбор, почему фильтр расходится) участник вручную переключается на `opus`
командой `/model opus`, а когда вывод закончен, возвращается на `sonnet`.

## Субагенты — штатная часть работы (D-016)

Субагенты запускаются по конвейеру ниже, не только по особому запросу. Роли те же, что и
раньше: что каждая видит, может и возвращает — в таблице и в `.claude/agents/*.md`.
Координатора по-прежнему нет: субагентов запускает основная сессия участника для своей
issue, а не кто-то за всю команду.

| Роль | Модель | Когда звать | Видит и может | Возвращает |
|---|---|---|---|---|
| `builder` | sonnet | реализация issue размера M и больше целиком; вторая issue участника параллельно с первой | свой worktree; полный набор инструментов; контракт и зависимости не меняет | PR, отчёт с командами и таблицей «было → стало» |
| `reviewer` | sonnet | **каждый PR с кодом, тестами, `params.yaml` или `.claude/` — перед merge**; для контракта, формата метрик и ядра оценщика — обязательно | только diff против `origin/main`; ничего не правит | вердикт `merge` / `доработать` / `человеку` с `файл:строка` |
| `evaluator` | sonnet | **таблица «было → стало» для каждого PR, меняющего поведение ядра или ноды** (как только `tools/eval` в `main`); чекпоинты; стенд жюри | `tools/eval`, `docker/jury-stand.sh`; пишет только в `docs/verification/` | таблицы с командами и commit |
| `scribe` | sonnet | issue по документам (`area:docs`, `area:docs-model`); документ разошёлся с кодом | worktree; выполняет команды, которые описывает | документы, список `TBD` |
| `jury` | opus | чекпоинты Ч0/Ч1/Ч2 и перед сдачей (режим 1); репетиция питча (режим 2) | только артефакты; ничего не правит | баллы 30/35/20/15 и питч 10/12/8, топ-5 действий; или 15 вопросов |

### Конвейер issue

```
основная сессия: issue → план с человеком
   → код: сама (S) или builder (M+) в worktree issue
   → evaluator: holdout «было → стало» против origin/main   ┐ параллельно,
   → reviewer: diff → вердикт                                ┘ одним сообщением
   → доработать → тот же builder (SendMessage) или сама → reviewer заново
   → merge по GIT.md («Финиш»)
чекпоинт: evaluator (holdout + stress + стенд) → jury (режим 1) → итог в HANDOFF.md
```

- Независимые субагенты запускаются одним сообщением параллельно: `reviewer` и
  `evaluator` на один PR, `jury` и `evaluator` на чекпоинте.
- Несколько `builder` одновременно — только на **разных** issue, каждая назначена на
  человека, у каждой свой worktree. Worktree создаёт основная сессия по `GIT.md`
  (`git worktree add .claude/worktrees/<N>-<тема> -b worktree-<N>-<тема> origin/main`) и
  передаёт путь в бриф. `isolation: worktree` у инструмента Agent не использовать: он даёт
  свои имена веток, и перестают работать правила уборки.
- Правило областей действует и для субагентов: две issue с одной `area:` параллельно не идут.
- Упёрлись в лимит — ждём сброса или делаем шаг в основной сессии. Шаг проверки
  (`reviewer`, `evaluator`) из-за лимита не пропускается.

Как звать: «builder: issue #12, worktree /…/.claude/worktrees/12-slip-detector»,
«reviewer на PR #17», «evaluator: сравни ветку worktree-12-slip-detector с origin/main на
holdout», «jury: режим 2». Правила проекта агенты получают из `CLAUDE.md` сами, поэтому в
промпте роли только то, что её отличает.

## Что нужно знать

- Субагент запускается в каталоге сессии. Если сессия открыта через `claude -w`, это уже
  worktree issue. Для второй issue путь её worktree передаётся в бриф.
- `reviewer`, `jury` файлы не правят. `evaluator` пишет только `docs/verification/`.
- Хук `SubagentStop` (`check-worktrees.sh`) проверяет секреты во всех worktree после
  каждого субагента.
- Отчёт субагента человек не видит: основная сессия пересказывает главное — числа,
  вердикт, что ждёт решения.
- Изменение контракта, новая зависимость, сокращение объёма условий решаются не агентами
  между собой: их выносят людям через PR с апрувом потребителей.

## Точки сборки команды

Синхронных созвонов-оркестраторов нет. Есть две общие отметки в день (время — в плане):
`main` зелёный, `tools/eval` на holdout по `main` записан в `docs/verification/`, итог и
блокеры — две-три строки в `HANDOFF.md`.
