# Данные организаторов

Что лежит в датасете, как его получить и прочитать, и чем он отличается от собственного
README организаторов. Все числа — из команд ниже на данных от 2026-09-25; сводка по каждому
bag — [`docs/data/survey.csv`](data/survey.csv), карта всех прогонов — [`docs/data/routes.png`](data/routes.png).

## Где взять и куда положить

Источник — <https://disk.yandex.ru/d/DdnscmWTBtzkOQ>: `data.zip` (254 МБ), `README.md`,
`tram_vehicle_msgs/`. В git не хранится.

```bash
# в основной копии репозитория
mkdir -p dataset && cp <скачанное>/{data.zip,README.md} dataset/ && cp -r <скачанное>/tram_vehicle_msgs dataset/
unzip -q dataset/data.zip -d dataset/data        # 122 каталога, 826 МБ
cp .env.example .env                              # TRAM_DATA_DIR — абсолютный путь к dataset/data
```

`dataset/` в `.gitignore`. Из worktree скрипты находят данные сами: `TRAM_DATA_DIR` из `.env`,
иначе `<основная копия>/dataset/data` (через `git rev-parse --git-common-dir`).

## Как читать

```bash
# без ROS (хост): сводка по всем bag за ~25 с на 6 процессах
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/python tools/survey/survey_bags.py            # -> docs/data/survey.csv
.venv/bin/python tools/survey/plot_routes.py            # -> docs/data/routes.png

# с ROS (контейнер, сеть не нужна)
bash docker/dev.sh bash -c 'colcon build --packages-select tram_vehicle_msgs && . install/setup.bash && ros2 bag info /data/30618_0e41eac3'
```

## Контракт жюри (из README организаторов, дословно по смыслу)

- Выход: `/result/velocity` (`tram_vehicle_msgs/msg/VelocitySensor`, поле `velocity`, м/с) и
  `/result/position` (`nav_msgs/msg/Odometry`, `pose.pose.position`, м).
- `header.stamp` — время соответствующего **входа из bag**, не wall clock. Судья сопоставляет
  с эталоном по ближайшей метке с допуском **~0,05 с**; нулевые/сбитые stamp — метрика не считается.
- Положение — в **локальной метрической системе, согласованной с эталонной траекторией**;
  сравнение покомпонентно `x/y/z` и по 3D-расстоянию. Эталон строят организаторы из GNSS.
- QoS судьи — best-effort, наш издатель может быть reliable.
- Только онлайн-публикация во время `ros2 bag play`; пакетная постобработка не засчитывается.
- GNSS в контуре — только начальная выставка/инициализация; в проверочных прогонах он есть
  «первые несколько секунд». Офлайн-калибровка параметров разрешена.

## Известные ловушки данных (проверено 2026-09-25)

1. **Скорость тележек — в км/ч, а не в м/с**, как пишет README. Отношение |колесо| / |GNSS vel|
   на движении (> 3 м/с): медиана **3,599**, по bag от 3,544 до 3,658. Максимум колеса 53,7 при
   максимуме GNSS 15,9 м/с. Перевод `× 1/3,6` — ровно в одном месте (preprocess, D-003).
   Выход `/result/velocity` — в м/с, как требует README (открытый вопрос организаторам — `HANDOFF.md`).
2. **Масштаб колеса разный у трамваев и плавает**: 30618 — 3,596 ± 0,010, 30639 — 3,611 ± 0,024
   (разброс ±1,5 %). Это износ/радиус колеса: 1 % масштаба = 1 % дрейфа положения. Нужна
   калибровка по GNSS в первые секунды и/или онлайн-оценка масштаба в фильтре.
3. **Побайтные дубликаты**: 25 пар bag с разными именами и одинаковым `.db3`. Если одна копия
   в train, а другая в holdout, метрика завышена. Список — `tools/eval/splits.yaml: dups`.
4. **В `tram_vehicle_msgs/package.xml` организаторов нет `<maintainer>`** — `colcon build` в Humble
   падает (`Package 'tram_vehicle_msgs' must declare at least one maintainer`). В нашей копии
   `src/tram_vehicle_msgs` добавлена одна строка maintainer, `.msg` не тронуты (D-006).
   Если у жюри свой `tram_vehicle_msgs` в том же workspace — будет конфликт имён пакетов:
   инструкция в README говорит, как исключить наш (`touch src/tram_vehicle_msgs/COLCON_IGNORE`).
5. **`header.stamp` отстаёт от времени записи bag**: медиана 50 мс у тележек, но в начале
   прогона — пачка буферизованных сообщений с отставанием до **3,7 с** (p99 > 2 с в 10 % bag).
   Время для модели — только `header.stamp`; порядок прихода ≠ порядок stamp.
6. **Немонотонные stamp**: до 6–7 откатов назад у тележек и до 20 у контроллера в одном bag.
   Сообщение со stamp из прошлого нельзя просто интегрировать — dt < 0.
7. **Дыры в одной тележке**: у 30639 задняя тележка молчит до **73 с** (`30639_3b3d9eb8`),
   47 с, 26 с, 20 с…; у `30639_c31df386` 20 с молчит передняя. Во всех 30618 одновременные
   паузы обеих тележек и контроллера ~1,05–1,3 с.
8. **Расхождение тележек** (> 1 км/ч больше 1 % времени движения) — только у 30639: 6 bag,
   до 10,6 % времени (`30639_3b3d9eb8`, p99 |Δ| = 23,8 км/ч). Главный материал для
   детектора проскальзывания/отказа датчика: 2 из них в train (2026-05-05), 4 в holdout (2026-08-26).
9. **Контроллер: 20 Гц и два издателя** (`offered_qos_profiles` из двух записей), при этом
   повторов stamp нет — поток один, с шагом 50 мс. Скорости — 10 Гц: синхронизировать по stamp.
10. **GNSS**: в 20 уникальных bag его нет совсем (эталона нет — только для модели привода); в 8
    bag дыры 5–29 с в середине; статус 0 и 2 перемешаны; в начале некоторых прогонов — одиночные
    выбросы позиции на километры (`routes.png`, точки внизу слева). Эталон для метрик — фильтровать.
11. **GNSS vel — в ENU, не в осях вагона**: продольная скорость = `hypot(x, y)`, знак движения
    из неё не получить. Колёса тоже без знака (отрицательных нет): задний ход не различим.
12. **Две антенны**: master и rover разнесены на **12,4 м** (p5–p95: 12,3–13,7) — курс вагона
    можно взять по базе antenna → antenna в разрешённые первые секунды даже на стоянке.
13. **Короткие прогоны** (1,3–54 с, 8 шт.): без движения или почти без — метрики дрейфа на них
    бессмысленны (деление на ~0 м пути), eval обязан это обрабатывать.

Ловушки 14–18 — `.venv/bin/python tools/survey/probe_route.py` (97 уникальных bag train,
holdout и no_gnss_train; масштаб — из `survey.csv`), проверено 2026-09-25.

14. **В окне GNSS трамвай стоит всегда**: в первые 5 с передняя тележка не превышает 1 м/с
    ни в одном из 97 bag. Калибровка масштаба колеса по GNSS в окне (D-005) не сработает ни
    разу; курс по скорости GNSS в окне тоже не получить.
15. **Rover стоит впереди master по ходу** во всех 70 bag с GNSS и движением: cos угла между
    базой rover → master и первыми 30 м пути — от −1,00 до −0,84 (30618, 53 bag) и от −1,00
    до −0,92 (30639, 17 bag), база 12,4 м. Курс и ветку карты можно выбрать на стоянке:
    направление движения = master → rover.
16. **Нода не знает номер вагона**: `frame_id` у тележек обоих трамваев `base_link`, у GNSS
    `gps`, у контроллера пусто (зонд смотрит по одному bag на трамвай). Выбрать масштаб «по трамваю» нельзя.
17. **Масштаб колеса плавает между днями**: 30639 — 3,631 ± 0,012 на train (05.05) и
    3,588 ± 0,002 на holdout (26.08), −1,2 %; 30618 — 3,598 ± 0,002 и 3,588 ± 0,017. С
    константой 3,6 ошибка масштаба на holdout: медиана 0,20 %, p90 0,62 %, максимум 1,56 %;
    дрейф к концу прогона только от неё — медиана 11 м, максимум 81 м. Офлайн-масштаб между
    днями не переносится, абсолютный масштаб по колёсам и модели не наблюдаем — нужна внешняя
    опора после окна: места остановок (ловушка 18, онлайн-масштаб D-034).
18. **Места остановок повторяются**: на train 486 остановок ≥ 10 с (скорость GNSS < 0,2 м/с)
    в 47 bag сводятся к 32 местам, где стояли в ≥ 5 bag; точка остановки от центра места —
    медиана 1,1 м, p90 7,0 м. На holdout 271 остановка, 84 % ближе 10 м к месту из train,
    92 % ближе 20 м, медиана 12 остановок на bag. Ядро привязывает путь к местам
    `maps/stops.csv` по дуге своей ветки (D-034: 34 места, другая методика — Доплер < 0,3 м/с
    ≥ 5 с, кластер по дуге): соседние места одной ветки бывают в 17,8 и 24,5 м (медиана 221 м).
    При ошибке вдоль пути больше половины такого интервала (~9 м) ближайшее место — соседнее, и
    привязка переносит ошибку, а не снимает её; гейт `stop_snap_max_m = 20 м` (D-039) от этого
    не защищает (#81). Числа в 2D по обоим направлениям (соседи в 30 м) для привязки по дуге не годятся.

## Что следует для решения

- Без IMU направление движения неоткуда взять, кроме **карты маршрута**: колёса дают только
  путь `s`. Маршрут один — карту (полилинию обоих направлений) строим офлайн из GNSS train
  (разрешено как офлайн-калибровка), положение = точка карты на дуге `s` от начальной
  привязки. Без карты x/y — прямая по начальному курсу, ошибка в сотни метров на первом повороте.
- Скорость: колёса после перевода единиц уже близки к GNSS (масштаб 0,999…1,016); выигрыш
  модели — в проскальзывании, дырах и выбросах, а не в штатном режиме.
- Масштаб колеса — главный остаток ошибки вдоль пути (ловушки 14, 16, 17): ни окно GNSS, ни
  номер вагона его не дают. Опора — места остановок из карты (ловушка 18, D-034).
- Разбиение train/holdout — по дням (`tools/eval/splits.yaml`, D-011).
