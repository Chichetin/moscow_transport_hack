## Дополнение 18: уже влитый D-064 / PR #114

**`docs/model.md:32` на `c1920c5` → `Preprocessor._wheel:141–171` → дополнить формулу
нормализации и различать сырой ноль и отрицательное измерение.**

Код сначала проверяет конечность и stamp, вычисляет масштабированную скорость,
затем при `kmh < 0` устанавливает `speed=0`. Отрицательный отсчёт не получает
исключение гейта ускорения, которое есть у сырого ровно нулевого показания:
при `|speed−prev.speed|/dt > max_wheel_accel_mps2` он отклоняется. На стоянке
может пройти как 0 м/с; в движении резкий переход отбрасывается. Это уже поведение
main, не ожидаемая правка #110.

Предлагаемое описание:

```text
v_scaled = u_i · input.wheel_speed_scale · vehicle.wheel_scale_i
v_i = 0, если u_i < 0; иначе v_scaled
```

Далее идут абсолютный предел скорости и гейт ускорения. Формула описывает
нормализацию кандидата, а не гарантию его принятия. В замечании 4 ниже «падение до
ровно нуля» относится к сырому нулевому показанию; искусственный ноль из отрицательного
отсчёта обрабатывается иначе.

Код: [Preprocessor на c1920c5](https://github.com/Chichetin/moscow_transport_hack/blob/c1920c504b73dd43f81cb95a5cd7c3ce26b9a677/src/tram_odometry_core/tram_odometry_core/preprocess/__init__.py#L141).
Доказательства автора изменения: [отчёт #111](../verification/2026-09-26-issue111-negative-kmh.md).
Числа этого отчёта «поверх #110» относятся к экспериментальному сочетанию веток;
они не означают, что #110 влит. Исходный D-058 ниже остаётся историей принятия #11,
а не оценкой текущего stress после #114.

**Конкретные правки перед merge**

1. **`docs/model.md:3,21,42,48,78,85,151` → `pipeline.py:117–124,149–160`, `SpeedFilter.predict/update/state` (`estimator/__init__.py:49–163`) → заменить устаревшее описание оценщика.** В main скорость уже берётся из `SpeedFilter`, не из `Σwᵢvᵢ/Σwᵢ`; `Estimate.accel = a_model+b`, не ноль. Прогноз `v⁻=max(0,v+(a_model+b)dt)` работает и при доступных измерениях, затем обновляется только новым отсчётом. При отсутствии доверия остаётся этот же прогноз. `drive.use_model=false` задаёт `a_model=0`, но не отключает `b` и фильтр, поэтому обещание «скорость удерживается» неверно. 2. **`docs/model.md:149–157` → `estimator/__init__.py:29–35,49–65,89–147,149–163` → привести фактическую математику фильтра и честно назвать состояние.** Это двухкомпонентное состояние `[v,b]`, матрицы `F=[[1,dt],[0,1]]`, `Q=[[q_accel·dt+q_bias·dt³/3,q_bias·dt²/2],[q_bias·dt²/2,q_bias·dt]]`, `P⁻=FPFᵀ+Q`. Относительный масштаб `δ` хранится и сглаживается отдельно, в `x/P` его нет. Ускорение модели считается внешним входом; код не берёт производную `model_accel(v)` или ограничения `max(0,…)` для F. Поэтому «EKF скорости» как название issue допустимо, но обещать совместный EKF скорости/ускорения/двух масштабов или полную линеаризацию физической модели нельзя. Для измерения указать `age=t_filter−t_sample`, `k_front=1−δ`, `k_rear=1+δ`, `z=v_i/k_i+a_model·age`, `R=r_wheel/(trust·k_i²)+q_accel·age`, `H=[1,−age]`, `ν=z−Hx`, `S=HPHᵀ+R`, `NIS=ν²/S`, принятие при `NIS≤nis_gate`, `K=PHᵀ/S`, `x←x+Kν` с ограничением `v≥0`, ковариацию Джозефа. Дать ссылки именно на `predict`, `update`, `_observe_scale`, `state`. Первый доверенный отсчёт инициализирует скорость без обычного NIS-гейта; до гейта есть расширение P при подтверждённых нулях и допустимом трогании. Эти исключения нужны для точного описания.

3. **`docs/model.md:102–109,164` → `slip/detector.py:53–111` → добавить D-054 с порядком условий.** Скачок определяется остатком `r_i=(v_i−v_i_prev)/(t_i−t_i_prev)−a_model`, условие `|r_i|>slip.noise_accel_mps2`, запоминаются отдельно знаки, удержание `0≤t_now−t_jump≤slip.noise_hold_s`. При двух живых тележках **сначала** согласие `|v_f−v_r|≤tol` даёт 1/1, затем проверяется специальный случай одного нуля. Только после них: недавние синфазные скачки без противофазной пары → 0/0 и оба slip-флага; противофазная пара → 0,5/0,5 без обоих флагов. Поэтому фраза «согласное проскальзывание обеих тележек не обнаруживается» слишком общая: часть синфазного юза распознаётся. Честное ограничение: одинаковое/достаточно близкое проскальзывание в пределах `tol` и медленное общее смещение этой эвристикой не выявляются. При 0/0 текущий фильтр прогнозирует `a_model+b`; доверие 0,5/0,5 само по себе **не означает**, что текущий фильтр выдаёт арифметическое среднее пары.
