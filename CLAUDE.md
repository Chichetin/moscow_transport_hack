# CLAUDE.md — правила работы над проектом

Хакатон Московского транспорта, кейс **«Резервная одометрия по модели»**. Задача:
пакет(ы) ROS 2 Humble, которые по позиции контроллера водителя и скоростям двух тележек,
без GNSS и IMU, в реальном времени оценивают скорость и положение трамвая и публикуют
`/result/velocity` и `/result/position`. Проверяет автоматический судья жюри на отложенных
bag, потом питч.

Условия — `task.md` (дословно). Данные и их ловушки — `docs/data.md` (**прочитать до кода**).
Контракты — `docs/contracts.md`, решения — `docs/decisions.md`, матрица условий —
`docs/tz-compliance.md`, области — `docs/project-structure.md`, план — `docs/plans/`,
Git — `GIT.md`, блокеры и итоги дня — `HANDOFF.md`.

Сдача — **27 сентября 2026, 23:59 МСК**, от 25.09 это ~2,5 дня. Последние ~6 часов —
только проверка сдачи и питч. Команда — пять равноправных участников, у каждого свой
Claude Code.

## Как здесь выигрывают

| Критерий | Баллы |
|---|---|
| Точность положения: дрейф %, along-track MEAN/MAX/RMSE, cross-track, корректный `Odometry` | **35** |
| Точность скорости: RMSE/MAE, bias на разгоне/торможении/остановках | 30 |
| Устойчивость: проскальзывание, пропуски, выбросы, нода не падает, диагностика | 20 |
| Реальное время: ≤ 100 мс (пик 250), ≥ 10 Гц, ≤ 2 ядра, ≤ 0,5 ГБ, colcon без сети | 15 |
| Питч: выступление 10, глубина 12, ответы 8 | 30 |

Выводы:

- **Положение — самый дорогой критерий, и без карты его не взять.** Колёса дают путь `s`,
  направления без IMU нет. Маршрут в данных один, поэтому карта строится из GNSS train
  (D-007). Без неё x/y расходятся на сотни метров на первом повороте.
- **Скорость почти бесплатна после перевода км/ч → м/с** (D-003). Баллы здесь теряются на
  юзе, дырах датчиков и на bias при торможении, а не в штатном ходе.
- **Реальное время и сборка — это пороги, а не шкала.** Нода, которая не собирается
  офлайн или падает на пропуске датчика, обнуляет всё остальное. Стенд жюри гоняем с
  первого дня.
- **Глубина на питче (12) — это модель и данные.** Ловушки из `docs/data.md` и
  идентификация привода с графиками — лучший материал. Решения записываются сразу.

## Команда и интеграция

- **Задачи — GitHub Issues.** Взять = назначить себя assignee (`gh issue edit N
  --add-assignee @me`). У issue есть метка `area:` и строка «Зависит от #…». **Не брать
  issue с той же `area:`, если на ней уже есть assignee в работе.** Кто что делает, видно в
  начале сессии (`session-context.sh`).
- **Контракты — единственная точка стыковки** (`docs/contracts.md`, `types.py`, имена в
  `params.yaml`, формат метрик, `splits.yaml`). Изменение — отдельный PR с перечнем
  потребителей; merge после апрува каждого из них. Молча поменять общий тип под свой модуль нельзя.
- **Спор решает метрика.** PR, ухудшающий главные метрики holdout против `origin/main`
  (D-012), не вливается. В описании PR — таблица «было → стало» с командой.
- **Сквозной путь в первый вечер:** bag → заглушки всех блоков → `/result/*` → метрика.
  Дальше каждый улучшает свой блок и видит прирост на той же таблице.
- **Маленькие PR, часто.** Незаконченное вливается неподключённым (не вызывается из
  `pipeline.py`), а не копится в ветке.
- **`main` всегда зелёный:** перед push `git fetch --prune && git merge origin/main` и
  полный прогон. Сломал `main` — чинишь раньше своей задачи.
- `HANDOFF.md` — только блокеры и итоги дня, не занятость.

## Неподвижные ограничения (task.md и README данных)

- Вход в основном контуре — только `/vehicle/front_bogie_velocity`,
  `/vehicle/rear_bogie_velocity`, `/vehicle/driver_position_cmd`. Без IMU.
- GNSS (`/sensing/gnss/{master,rover}/{fix,vel}`) — только начальная выставка в первые
  `gnss.init_window_s` секунд (D-005). Использование позже — дисквалификация.
- Выход: `/result/velocity` (`tram_vehicle_msgs/VelocitySensor`, м/с) и `/result/position`
  (`nav_msgs/Odometry`); `header.stamp` = время входа из bag, `frame_id` заполнен.
- Только онлайн, без данных из будущего и без пакетной постобработки.
- Реальное время: задержка ≤ 100 мс (пик ≤ 250), ≥ 10 Гц, ≤ 2 ядра, ≤ 0,5 ГБ, без утечек.
- `colcon build` без интернета, ROS 2 Humble. В рантайме только apt-пакеты Humble (D-004).
- ML разрешён, если обучен только на разрешённых данных и работает в реальном времени.
  Офлайн-калибровка параметров разрешена.

## Модель и данные

- Единицы внутри — СИ. Тележки приходят в **км/ч**, перевод ровно в одном месте (D-003).
- Время — только `header.stamp`. Порядок прихода ≠ порядок stamp; бывают откаты назад и
  пачки с отставанием до 3,7 с (`docs/data.md`, ловушки 5–6).
- Датчик может молчать до 73 с. Модель должна ехать на прогнозе, а не стоять и не взрываться.
- Масштаб колеса разный у трамваев (±1,5 %): 1 % масштаба — это 1 % дрейфа положения.
- Train/holdout — по дням (`tools/eval/splits.yaml`, D-011). Holdout не используется для
  настройки. Побайтные дубликаты исключены.
- Данные в git не кладутся: `TRAM_DATA_DIR` (`.env`) или `<основная копия>/dataset/data`.

## Код и архитектура

- Ядро `tram_odometry_core` — чистый Python + numpy **1.21** (D-004): без `rclpy`, без
  scipy, без API numpy ≥ 1.22. ROS-ноды `tram_odometry` — тонкие обёртки. Оба
  потребителя (нода и `tools/eval`) зовут один `pipeline.Odometry.step`.
- Язык обёртки выбирается по замеру на стенде (D-002), а не по вкусу.
- Модуль ядра импортирует только `types.py` и numpy. Соседей он видит только через `pipeline`.
- Параметры — только `params.yaml` с единицами в комментарии. Магических чисел в коде нет.
- На каждое сообщение: O(1) по времени и памяти, без роста буферов, без логирования.
- Плоский код: функции и dataclass. Без фабрик, реестров и конфиг-движков «на будущее».
- Идентификаторы и комментарии в коде — английские, документы — русские.
- Правки только в своей `area:`, соседний код не переформатировать.

Команды:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt   # один раз
.venv/bin/python -m pytest                          # ядро и tools, без ROS
```

## Тесты и доказательство результата

- Новая логика → тест в том же коммите. Багфикс начинается с воспроизводящего теста.
- Обязательные тесты: перевод единиц; немонотонный/повторный stamp; молчащая тележка;
  NaN/inf на входе; выход `Odometry` заполнен по контракту; stamp выхода = stamp входа;
  GNSS после окна игнорируется.
- Прирост модели — только числом `tools/eval` на holdout, с командой и commit. Train — для
  настройки, не для отчёта.
- Реальное время — только замер на стенде жюри (`docker/jury-stand.sh`), не оценка «на глаз».
- **Нет команды и вывода — нет «работает».** Ни в чате, ни в PR, ни в README.
- Stop-хук `check-tests.sh` сам находит pytest (и `colcon test` в контейнере) и не даёт
  закончить ход с красными тестами. Пока тестов нет, он молчит.

## Принципы Карпаты — под эту задачу

1. **Become one with the data.** Прочитать `docs/data.md` и открыть графики скорости
   колёс и GNSS на 2–3 bag до модели. Каждая ловушка там стоила кому-то вечера.
2. **Тупой бейзлайн прежде умного.** Среднее двух тележек / 3,6 + интеграл по карте — это
   первая строка таблицы. EKF обязан её побить на holdout, иначе он не нужен.
3. **Overfit one bag first.** Модель привода сначала сходится на одном длинном bag train,
   потом на всех.
4. **Визуализировать всё.** Скорость, ошибка, флаг проскальзывания и позиция контроллера на
   одной оси времени. Графики нужны и для отладки, и для питча.
5. **Не доверять одному числу.** Смотреть медиану и худший bag, режимы разгон/торможение/стоянка.
6. **Фильтр молча врёт.** Инновации и их нормированный квадрат (NIS) логировать в eval.
   Расходящийся фильтр выглядит как «чуть хуже».
7. **Журнал решений.** Решение — строка в `docs/decisions.md`. Это материал для питча.

## Работа с Claude Code

- Формат команды — `docs/agents.md`. Каждый участник — одна сессия в своём worktree на
  одну issue. Модель по умолчанию `sonnet`; `opus` включают вручную на математику модели
  и фильтра.
- Субагенты — штатная часть работы (D-016), конвейер — `docs/agents.md`: `builder`
  (реализация issue M+), `evaluator` (таблица holdout для PR, стенд, чекпоинты),
  `reviewer` (каждый PR с кодом, тестами, `params.yaml` или `.claude/` перед merge), `scribe` (документы), `jury`
  (чекпоинты и вопросы питча, `opus`). Независимые — параллельно одним сообщением.
- Скилл `submission-checklist` — проверка комплекта сдачи.
- `docs/tz-compliance.md` обновляется в том же PR, что и артефакт.
- Хуки: `session-context.sh` (ветка, мои issues, занятые области), `check-secrets.sh`,
  `check-tests.sh`, `check-upstream.sh` (чужие коммиты в твоих файлах и контрактах),
  `check-worktrees.sh`. Проверка хуков: `bash .claude/hooks/test-hooks.sh`.
- `check-upstream.sh` показал чужой коммит в твоих файлах или контрактах — оценить, не
  противоречит ли задаче. Противоречит — остановиться и сказать человеку.

## Ревью

- Каждый PR с кодом, тестами, `params.yaml` или `.claude/` — вердикт `reviewer` перед
  merge. Контракт, формат метрик, `splits.yaml` — ещё и апрув потребителей-людей.
- Чек-лист: GNSS после окна не используется; км/ч → м/с в одном месте; stamp выхода = stamp
  входа; тест есть; таблица holdout «было → стало»; numpy 1.21; решение записано.

## Git

Кратко (полностью — `GIT.md`): задача делается **в своём worktree**
(`claude -w <issue>-<тема>` → `.claude/worktrees/<issue>-<тема>`, ветка
`worktree-<issue>-<тема>`), в `main` — через PR (`gh pr create`, в описании `Closes #N`)
или прямым push `git push origin HEAD:main` на тех же условиях (D-017).
Коммит и push ветки — **без запроса разрешения** после каждого проверенного шага; в коммит
только свои пути (`git add <пути>`); force-push, rebase, amend, `reset --hard`, `add -A`
запрещены; push в `main` агент делает сам, без force и только с зелёными проверками. Трейлеры
соавторства ИИ не добавляем.
