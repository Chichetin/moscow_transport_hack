# tools/stand — замеры реального времени по записи стенда жюри

`docker/jury-stand.sh <bag>` запускает ноду в контейнере (2 CPU, 512 МБ, без сети), играет
bag, пишет `out/stand/<bag>/record` (rosbag2: входы и `/result/*`) и `resources.csv`
(`sampler.py`, раз в секунду, по `/proc`: тики CPU и RSS процессов, в чьей командной строке
есть `odometry_node`; лаунчер `ros2 launch` не входит). В конце стенд зовёт

```bash
.venv/bin/python tools/stand/run_stand.py out/stand/<bag>     # таблица + stand.json
```

| Показатель | Как считается | Порог (`task.md`, критерий 4) |
|---|---|---|
| задержка p50/p99/max | время приёма выхода − время приёма входа с тем же `header.stamp` (совпадения FIFO; выход без входа — `unmatched`) | p99 ≤ 100 мс, max ≤ 250 мс |
| частота | выходов / длительность по времени приёма; берётся меньшая из `/result/velocity` и `/result/position`; топик без сообщений — 0 Гц | ≥ 10 Гц |
| CPU | Δтиков процессов ноды / (CLK_TCK · Δt), сумма по процессам, в ядрах | max ≤ 2 ядра |
| RSS | сумма RSS процессов, пик | ≤ 512 МБ |
| рост RSS | наклон МБ/мин по последним 2/3 прогона | ≤ 1 МБ/мин (наш порог утечки, D-023) |

Ограничения: задержка — по времени приёма записью (`ros2 bag record` — тот же хост и часы), это
включает очередь DDS и работу ноды, но и накладные расходы самой записи; CPU — только процессы
ноды, без `ros2 bag play/record`. Проверено на синтетической записи и модульными тестами
(`tools/stand/tests`); на реальной ноде — после #5.

Для приёмки нужен `RATE=1.0`: время приёма — wall clock, при другом темпе `bag play` частота
выходов масштабируется. Если входы разных топиков имеют одинаковый `stamp`, выход сопоставляется
с самым ранним из них — оценка задержки консервативна (завышена). Шаблон процесса ноды
(`ODOM_PATTERN`, по умолчанию `odometry_node`) не должен совпадать с именем launch-файла, иначе в
замер попадёт `ros2 launch`.

Тесты: `.venv/bin/python -m pytest tools/stand`.
