# tools/eval — метрики без ROS

Читает bag библиотекой `rosbags`, подаёт сообщения в `tram_odometry_core.pipeline.Odometry`
**в порядке записи**, как их публикует `ros2 bag play` (с откатами и опозданиями `header.stamp`,
ловушки 5–6 `docs/data.md`). **GNSS обрезается после первых `--gnss-window` секунд** от stamp
первого сообщения (по умолчанию = `gnss.init_window_s` из `params.yaml`, D-005). Эталон строится
из всего GNSS master прогона, считаются метрики критериев 1–2. Формат вывода и определения
метрик — `docs/contracts.md` §4 (контракт), уточнения — D-020. Наборы — `splits.yaml`
(контракт, D-011).

Статус: готово (#6). Бейзлайн P0 на holdout — `docs/verification/2026-09-25-pr35-baseline-holdout.md`
(Linux, 33 с); повтор на Windows-хосте с теми же числами — `docs/verification/2026-09-25-eval-holdout-windows.md`
(18 с). `--plot` — #16 (ниже), `--stress` — #15. Условие D-005 (GNSS после окна не меняет выход) — сквозной тест `tests/test_gnss_after_window.py` (#57, D-052).

```bash
.venv/bin/python tools/eval/run_eval.py --split quick         # 3 bag, цикл разработки, ~15 с
.venv/bin/python tools/eval/run_eval.py --split holdout       # решение о merge (26 bag)
.venv/bin/python tools/eval/run_eval.py --split holdout --compare out/eval/<base>-holdout/metrics.json
.venv/bin/python tools/eval/run_eval.py --bag 30639_d927f360 --bag 30618_e9a34502
.venv/bin/python -m pytest tools/eval/tests                   # тесты метрик на синтетике
```

`run_eval.py` — точка входа из корня репозитория (пакет лежит в `tools/eval/tram_eval`; из
`tools/eval` то же самое: `python -m tram_eval`). Данные — `TRAM_DATA_DIR` из окружения или
`.env`, иначе `<основная копия>/dataset/data`; результаты — `TRAM_OUT_DIR` (по умолчанию `out/`).

Одна команда → markdown в stdout (медиана и худший bag по каждой метрике; с `--compare` —
«было → стало → Δ %» и строка D-012) + таблица по bag + `out/eval/<commit>-<набор>/metrics.json`.
`<commit>` с суффиксом `-dirty`, если в отслеживаемых файлах есть незакоммиченные правки.

## Как считается (D-020)

| Что | Правило |
|---|---|
| Эталон положения | GNSS master `fix` → ENU (WGS84 через ECEF). Начало — как frame `map` трекера (D-030, D-050): первый fix статуса 2 в окне выставки, иначе первый валидный fix окна любого статуса, даже если точки трека — только статус 2 и он появляется позже (#70); без fix в окне — первая точка трека. Отброшены `status < 0`; если в bag есть фиксы `status = 2` (GBAS) — только они: при переключении 0↔2 трек прыгает на 1–9 м. Выбросы — дальше 15 м от скользящей медианы (21 точка) |
| Дуга эталона `s` | интеграл доплеровской скорости master `vel`: на стоянке 0, а длина трека из фиксов на ползущем трамвае растёт от блуждания на 0,5–1 м |
| Эталон скорости | `hypot(ve, vn)` master `vel`, выше 30 м/с — сбой |
| Сопоставление | для каждой точки эталона — оценка с ближайшим `Estimate.t` в пределах 0,05 с; оценка может выходить с любой частотой |
| Режимы скорости | ускорение эталона после среднего ±0,5 с: разгон > 0,2 м/с², торможение < −0,2; стоянка v < 0,3 м/с важнее разгона и торможения; остальное — ход |
| along / cross | оценка проецируется на трек эталона точка за точкой: окно вокруг прошлой дуги, шаг назад по дуге дороже шага вперёд (трамвай не ездит назад) — проекция не перескакивает на соседний путь обратного направления. Концы трека продлены по касательной, чтобы оценка впереди конца сохраняла ошибку. along = |s оценки − s эталона|, cross = расстояние до трека |
| drift % | горизонтальная ошибка в последней сопоставленной точке / дуга эталона между первой и последней; короче 50 м — `null` |
| pos3d | 3D, как у судьи: z оценки — `Estimate.z`, пока его нет — 0; высота эталона на маршруте меняется на десятки метров |
| Упала модель | исключение в `step` или в подсчёте метрик → `crashed = true` у этого bag, остальные bag считаются; метрики — по тому, что успело выйти |
| NaN/inf в оценке | такие `Estimate` (время, скорость или x/y/z) не участвуют в метриках: `n_matched` падает, bag пишется в stderr, сумма по прогону — в итоговой строке CLI рядом с `Estimate.t` ≠ stamp входа (D-015). В `metrics.json` этих счётчиков нет (формат §4). Главная метрика, пропавшая в ветке, для D-012 — «хуже» |

Нижняя граница метрик — «читер», который выдаёт эталон как оценку: along RMSE 0,02–0,13 м,
cross 0 на `quick` (разброс — допуск 0,05 с при 10 м/с).

Стресс (`--stress`, #15, D-040): генератор на holdout-bag — выбросы, пропуски 1–70 с одной тележки,
всплеск одной тележки («проскальзывание»), шум, дрожание и откаты stamp.

```bash
.venv/bin/python tools/eval/run_eval.py --split holdout --stress   # metrics.json как обычно + stress.json
```

Каждый сценарий — отдельный прогон pipeline по тому же bag, где изменены только сообщения
тележек в одном окне (`tram_eval/stress.py`, амплитуды фиксированы, без случайности). `noise`
меняет обе тележки противофазно; остальные сценарии меняют только переднюю. Если в окне нет
подходящих сэмплов для фактического возмущения или bag слишком короток, сценарий пропускается. Окно
начинается на 40 % длины bag, но не раньше чем через 1 с после конца окна GNSS прогона (то же
окно, что отрезает GNSS в `run_pipeline`) и не позже, чем за 3 с до конца. GNSS не меняется,
поэтому эталон тот же и выставку сбой не задевает.

| Сценарий | Что меняется (передняя тележка, если не сказано иное) | Длина |
|---|---|---|
| `outlier` | одно значение 180 км/ч | 0,2 с |
| `gap_1`, `gap_10`, `gap_70` | сообщения выброшены | 1, 10, 70 с |
| `spike` | +25 км/ч к каждому значению | 5 с |
| `noise` | ±3 км/ч синус, у задней в противофазе | 10 с |
| `jitter` | stamp ±0,04 с через одно | 10 с |
| `rollback` | каждое 10-е сообщение со stamp −0,35 с | 10 с |

`stress.json` (вне контракта §4, `metrics.json` не меняется): по bag и сценарию — окно
события, пик ошибки скорости и 3D-позиции против эталона во время события (`peak_*_error`),
тот же пик чистого прогона (`clean_peak_*`), пик добавки «возмущённый − чистый»
(`peak_*_excess`), время восстановления после конца события — первый момент, с которого
добавка ≤ 0,2 м/с (скорость) или ≤ 2 м (позиция) непрерывно 2 с без пропусков публикации
дольше 0,3 с (`null` — не восстановилось до конца bag), `crashed`. Если после окна GNSS и
1 с запаса событию с хвостом 3 с места нет — `skipped`. В stdout — сводная таблица по сценариям.

Графики (`--plot`, #16, D-048): после метрик по каждому bag — `<out>/plots/<bag>_timeline.png` и
`<bag>_xy.png` (нужен matplotlib из `requirements-dev.txt`; в dev-образе его нет, тесты
отрисовки там пропускаются). `metrics.json` не меняется.

```bash
.venv/bin/python tools/eval/run_eval.py --split quick --plot
.venv/bin/python tools/eval/run_eval.py --bag 30618_27e994fc --plot
```

| Файл | Что на нём |
|---|---|
| `_timeline.png` | одна ось времени от начала bag: скорость (оценка, эталон GNSS, обе тележки как записаны, м/с через `input.wheel_speed_scale`); оценка − эталон, м/с; ошибка вдоль пути со знаком (+ оценка впереди) и поперёк, м — та же проекция, что в метриках; позиция контроллера; флаги проскальзывания заливкой |
| `_xy.png` | карта `route.csv`, эталон и оценка в системе эталона eval (ENU `Reference.origin`, перевод карты — как в `PathTracker`, через ECEF); в заголовке — RMSE скорости, along и cross. С D-050 начало эталона — по правилу frame `map` трекера, поэтому система графика совпадает с frame трекера и на bag без статуса 2 в окне |
